# 次期リリースを計画する

次バージョンのスコープ決めフェーズを実行する：すでに存在するissueを見て、次に何を出すかを決め、そのためのマイルストーンを準備する。このスキルの仕事は、issueが既にトラッカーに存在している状態から始まり、マイルストーンを作成した時点で終わる。

`$ARGUMENTS` は目標バージョン（`v`無しで例: `0.2.0`）。空の場合は、どのissueを選んだか確定してから（手順4を参照）推定し、ユーザーに確認する。

## 手順

1. **現状を把握する** — `gh issue list --state open --limit 1000 --json number,title,labels,milestone,body` と `gh api repos/:owner/:repo/milestones --paginate --jq '.[] | {title,state,number}'` を実行する（棚卸しなので、デフォルトの取得件数制限で一部のissue/milestoneを見落とさないよう `--limit`/`--paginate` を必ず付ける）。あわせて `package.json` の現在の `version` を読む。すでにオープンなマイルストーンに入っている（スコープ決定済みの）issueは、ユーザーから指示がない限り対象外とする。

2. **不足しているラベルを補う** — このリポジトリではラベルを2軸で使う：種別（`bug` / `enhancement` / `documentation` / `refactor` / `ci` / `chore`）と優先度（`priority:high` / `priority:med` / `priority:low`）。まず `gh label list` でこれらが揃っているか確認し、無いものだけ作成する（`gh label create "priority:high" -c <hex> -d "..."` など。既存のラベルに対して作成コマンドを叩くとエラーになるので、無いものだけに絞る）。これによりラベルが一つも無いリポジトリでもこのスキル単体で完結する。そのうえで、種別/優先度ラベルが付いていない候補issueは、タイトルと本文を読んで判定する：
   - 種別: 内容から推測する（不具合報告 → `bug`、機能要望 → `enhancement`、ドキュメントのみ → `documentation`、挙動を変えない内部整理 → `refactor`、GitHub Actions/ワークフローの変更 → `ci`、依存関係更新など他のどれにも当てはまらない雑務 → `chore`）。
   - 優先度: ユーザーへの影響度、「整える」（正規化/マージ/フィルタ/折りたたみ/比較）のコアにどれだけ近いか、実装コストを勘案する。`backlog`（「まだスケジュールされていない将来のアイデア」）ラベルが付いているissueは、ユーザーが昇格を望まない限り明確に次バージョンの対象外とし、リリース優先度を付けない。
   - `gh issue edit <n> --add-label <種別> --add-label <優先度>` で付与する。

3. **候補issue間の前提関係・お得な順序を洗い出す** — 各候補issueの本文にある既存の依存関係のヒント（`関連: #N`、`前提: #N`、タスクリストの参照）を読み、`gh api repos/:owner/:repo/issues/<n>/sub_issues`（またはUI上の親issue情報を見るための `gh issue view <n> --json`）でネイティブな関係も確認する。「どのissueがどのissueより前に必要か」という**厳密な**依存リストを作る。前提issueそのものが今回選ばれていない（かつクローズもされていない）issueは今回選定できない——黙って外すのではなく、その矛盾をユーザーに提示する。
   - あわせて、厳密な依存ではないが「先にXXをやっておくとYYが安く済む」という**お得な順序**も見つけて記録する（例: リファクタ（`refactor`）してから機能追加（`enhancement`）すると手戻りが減る、共通処理を先に切り出すと後続issueの実装が楽になる、など）。これは選定可否には影響しないが、手順6の推奨着手順序に反映する。

4. **ユーザーとスコープを決める** — オープンな候補を表で提示する：番号、タイトル、種別、優先度、前提issue、次バージョンへの採否（推奨）。`AskUserQuestion` で、issueごとに1問ずつではなく、採否案全体（推奨をそのまま承認する／特定の項目を外す／`backlog` のissueを1つ昇格する、など）として確認する。

5. **バージョンの上げ方を決める** — 最終的な選定内容に基づいて：
   - 選ばれたissueの中に破壊的・非互換な変更がある → **メジャー**を上げる。
   - そうでなく、選ばれたissueの中に機能追加（`enhancement`）がある → **マイナー**を上げる。
   - それ以外（バグ修正/ドキュメント/雑務のみ） → **パッチ**を上げる。
   `package.json` の現在のバージョンから `vX.Y.Z` を計算し、`$ARGUMENTS` が未指定、またはこのルールと食い違う場合はユーザーに確認する。

6. **マイルストーンを作成する** — タイトルは `vX.Y.Z`。全マイルストーンを一覧して重複チェックするのではなく、まず作成を試み、重複エラーだけを見て分岐する：
   - `gh api repos/:owner/:repo/milestones -f title="vX.Y.Z" -f state="open" -f description="..."` を実行する。
   - 成功したら、それを使う。
   - `422`（同名重複）で失敗したら、`gh api "repos/:owner/:repo/milestones?state=all" --jq '.[] | select(.title=="vX.Y.Z")'` でそのタイトルのマイルストーンを取得する：
     - `state` が `open` ならそれを既存のマイルストーンとしてそのまま使う（再実行時に重複エラーにしない、というだけのための分岐）。
     - `state` が `closed` なら、そのバージョンは既にリリース済み（または誤ってクローズ済み）という異常な状態なので、作成・流用せずにユーザーへ報告する。
   マイルストーンの `description` は、他のセッションやスキル（例えば実装用のスキル）がユーザーに聞き直さずに計画を引き継げるよう、リリースの共有ブリーフとして書く：
   - リリースのテーマ・目的を一行で。
   - 選定したissueの**推奨着手順序**（厳密な依存関係を最優先、次にお得な順序、その次に優先度）。例: `1. #12 → 2. #9（#12に依存） → 3. #7（#15より先にやると安上がり） → 4. #15`
   - 見送った項目とその理由（前提未達、次バージョン以降に持ち越し、など）。

7. **文章だけでなく、issue単位の関係も設定する** — マイルストーンの説明文だけに順序情報を頼らない：
   - 選定した全issueをマイルストーンに割り当てる: `gh issue edit <n> --milestone "vX.Y.Z"`。
   - 本当に親issueをサブタスクに分割したような関係には、GitHubネイティブのsub-issues機能を使う: `gh issue edit <親> --add-sub-issue <子>`（または `gh issue edit <子> --parent <親>`）。これはIssues UI上に構造的な親子関係として残り、`gh api repos/:owner/:repo/issues/<n>/sub_issues` でも取得できる。
   - 親子関係ではない「先にこれが必要」という順序依存には、依存先issueの本文に `前提: #N` の一行を（まだ無ければ）追記する（GitHubが自動リンクし、サイドバーにも表示される）。

8. **報告する** — マイルストーンのURL/番号、選定したissue一覧（最終的なラベルと推奨順序付き）、スコープ外にしたissueとその理由を挙げる。各issueの実装はこのスキルの後段フェーズであり、そのフェーズはマイルストーンの説明文とsub-issueのリンクを読めば、ユーザーに聞き直さずに再開できる、という点も伝える。

## 補足

- これはスコープ決定用のスキルであり、成果物はマイルストーン・ラベル・関係性であって、コードでも新規issueでもない。棚卸し中に本当に足りていないものが見つかった場合は、ユーザーに伝えるにとどめ、ユーザーが望んだ場合のみマイルストーン未設定のissueとして別途起票する——新規提案はこのスキルのスコープ外。
- ラベルの2軸は独立に保つ：検討対象になったissueは、種別・優先度をそれぞれ1つずつ必ず持つ。
- 引き継ぎには独自フォーマットを発明するより、GitHub自体の仕組みを優先する：物語・順序はマイルストーンの `description`、親子関係はネイティブのsub-issues、単純な順序依存は自動リンクされる `前提: #N` のテキスト参照。こうしておけば、将来のどのセッション・スキルでも、マイルストーンとissueを読むだけでユーザーに聞き直さずに計画を再構築できる。
- 手順2・6・7でのラベル/マイルストーン作成やissue編集の `gh` 呼び出しが、実際に実行されたことを都度確認する。実行された呼び出しは、ツール結果・「バックグラウンドで実行中」の応答・エラーのいずれかを返す。ターンがそのいずれも無いまま終わり、ユーザーが次に発言した場合は、その呼び出しは実行されていない（構文ミスの可能性が高い）——実行されたと仮定せず、修正して再実行する。
